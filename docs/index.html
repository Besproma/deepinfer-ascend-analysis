并行、调度与模型级创新

DeepSeek V4.1 的一次请求会同时碰到几类等待：长上下文要求 Prefill 在更多设备间分摊计算，MoE 路由把延迟集中到最忙的专家，自回归 Decode 把生成拆成大量串行小步，缓存恢复和 CPU 排批又可能让设备空等。DeepInfer 的价值不在于堆叠更多并行名词，而是把模型已知的形状、稀疏模式和 KV 规则带进并行、通信与调度，让这些等待尽量不再落在关键路径上。

核心判断

推理变慢，常常不是设备算得慢，而是设备在等。

DeepInfer 针对固定模型重新安排工作分配、生成步数和模块边界，目标是把等待从首 token、每个 Decode step 和 MoE 往返中移走。

长上下文 一条请求拖住一组设备

数据并行能增加请求副本，却不能自动拆开单条长 Prompt。上下文越长，首 token 阶段越容易受最慢设备限制。

Balanced CP 分段并行
专家热点 最慢 rank 决定整轮时间

MoE 把专家铺到更多 rank 后容量更大，但 token 分发、热点专家和结果汇合都会形成新的等待。

EP + DeepEP + EPLB
逐 token 生成 一次迭代只能前进一格

标准 Decode 产生大量串行小步。小 batch 时算力宽度不足，权重读取与启动开销却仍要反复支付。

DSpark 多 token 验证
模块边界 CPU、通信与访存互相等

排批、多个 MoE kernel 和缓存恢复原本各自完成工作，却可能让 NPU 空转，或让同一份中间数据反复读写。

异步调度 + MegaMoE
01

先把一个大任务拆给更多设备

CP 与 EP 解决“算力铺不开”的问题。Balanced CP 处理单条长请求，MoE EP 扩大专家池，EPLB 再处理真实路由形成的新热点。

01

Balanced CP：让一条长请求也能多卡并行

并行 · 长上下文 Prefill

不是让更多请求同时运行，而是把同一条长 Prompt 拆成工作量接近的几段，让多张卡一起完成首 token 阶段。

原来的限制：Attention DP 擅长增加请求副本，却不会自动拆分单条请求。长 Prompt 仍由一组设备承担，而且只要某个 rank 分到更多 token，其他 rank 做完后也必须等待。

设计带来的变化：Balanced CP 按上下文切分，并尽量平衡各 rank 的 token 数和计算量。它同时扩大单请求可用的算力、缩小各 rank 完成时间差，因此缩短的是首 token 阶段的关键路径。

昇腾适配证据：2 节点 × 8 NPU 的离线 CI 使用 EP16 / CP8，覆盖这一并行组合；该配置对应功能验证口径，吞吐与时延按目标环境另行测试。

02

MoE EP + DeepEP：把专家容量扩到集群

并行 · 专家分发与汇合

EP 让不同专家分布到更多 rank；DeepEP 负责把 token 送到目标专家，再把结果送回原 rank。

为什么只扩卡不够：专家若集中在较小设备范围内，权重容量和并行算力都会受限。但引入 EP 后，token 的 dispatch 与 combine 会新增跨卡通信，通信路径做得不好，扩出去的算力会被等待抵消。

设计带来的变化：EP 把专家铺到多个 rank，DeepEP-Ascend 则使用 HCCL / HCOMM、UBMEM 与 URMA 等昇腾路径完成分发和回收。真正的收益来自“专家计算扩出去”与“通信成本降下来”同时成立。

昇腾适配证据：公开验证覆盖 EP128，dispatch 峰值 313–320 GB/s；数据口径为 950DT、验证版 HDK 与外部 Clos 网络，一般生产带宽按实际组网配置评估。

03

EPLB：让专家布局跟着真实请求热点移动

并行 · 负载再平衡

专家数量铺开以后，新的问题不是总量不够，而是少数热门专家排队；EPLB 的目标是压缩最忙 rank 的尾部工作量。

为什么固定布局会失效：训练完成时的专家放置对某类请求可能合理，但线上流量变化后，少数专家会持续成为热点。MoE 一轮依赖最慢 rank 完成，平均利用率再高也不能消除这部分等待。

设计带来的变化：EPLB 统计 token 负载，周期性调整专家放置，让各 rank 的热点更接近。它还必须控制权重迁移成本，否则“为了均衡而搬运”可能比原来的排队更贵。

昇腾适配证据：昇腾侧已覆盖负载统计、重排计算、在线权重同步与调度链路；权重 shuffle 使用通用 P2P 路径完成同步，后续可在平台对称内存接口就绪后接入单机镜像加速。

02

再减少必须串行执行的步数

并行只能分摊已经存在的工作。DSpark 减少主模型需要串行执行的 Decode 轮数，SWA bounded replay 则删掉对当前输出已无贡献的历史重算。

04

DSpark：把“一步一 token”改成“一次核验多个”

模型级 · 投机解码

先用较轻的方式提出多个 draft token，再由主模型一次验证；接受的前缀越长，一次串行迭代前进得越多。

原来的限制：标准自回归 Decode 每轮生成一个 token，再把它追加到上下文后调用下一轮。生成越长，串行次数越多，小 batch 时设备算力也很难被充分利用。

设计带来的变化：DSpark 先生成多个候选，再依据置信度决定验证深度。主模型接受正确前缀后，可从首个不匹配位置继续，因此净收益取决于接受率、验证成本和额外调度开销。

昇腾适配证据：DFlash、采样与调度在昇腾算子目录中已有对应实现；本次公开材料聚焦机制与算子路径，接受率、单位 token 成本和端到端加速比可按目标负载补测。

05

SWA bounded replay：不要重算已经失效的历史

模型级 · KV Cache

缓存恢复时只重放足够覆盖当前注意窗口的最短后缀，而不是把完整 Prompt 或整段历史 KV 再处理一遍。

原来的限制：通用缓存恢复如果不知道模型使用滑动窗口，通常会选择完整重放来保证正确性。窗口外的 token 已不影响当前输出，却仍要消耗 KV 读取、搬运和 Prefill 算力。

设计带来的变化：Decoder Prefill 只重放必要的有界后缀。V4.1 默认保留 140 tokens，并要求覆盖 SWA 窗口和最大回溯长度；收益大小取决于窗口配置、复用率与缓存命中。

昇腾适配证据：回放长度是明确配置，机制可审计；公开材料聚焦实现路径，不同缓存命中率下的时延与吞吐曲线可按目标场景测试。

03

最后把等待与数据搬运移出关键路径

即使每段计算都已经并行，CPU 排批、MoE 中间结果写回和多 kernel 同步仍会让 NPU 停下来。调度与算子融合解决的是这部分系统开销。

06

异步批调度：下一批在上一批执行时准备好

调度 · CPU / NPU 重叠

CPU 不再等 NPU 做完这一批才开始排下一批；请求检查、batch 拼装和元数据准备被藏进设备执行时间。

原来的限制：如果调度器和设备严格轮流工作，每一轮都要先花 CPU 时间准备，再花 NPU 时间执行。Decode 小 batch 执行很短时，排批等待会占掉更明显的比例。

设计带来的变化：CPU 侧调度与 NPU 执行重叠后，一轮耗时不再简单等于“CPU 时间加 NPU 时间”，而更接近两者中较长的一项。NPU Graph 还能降低 kernel launch 开销；组件级耗时可通过平台 profiling 与预留的 Graph Timer 接口联合分析。

昇腾适配证据：该调度默认启用，NPU Graph 可捕获和 replay；graph_timer_asc.cpp 已预留统一计时接口，组件级归因可结合目标 CANN profiling 工具完成。

07

MegaMoE：把多次 kernel 往返接成一条数据流

融合 · MoE 数据路径

专家分发、矩阵计算、SwiGLU 与结果汇合不再各做各的，而是在同一条数据流中协同布局，减少中间结果的写入和再读取。

原来的限制：dispatch、grouped GEMM、SwiGLU 和 combine 若分别作为独立 kernel 执行，每一步都要从前一步写回的中间张量重新读取，同时增加 buffer 占用、kernel 启动和同步点。

设计带来的变化：MegaMoE 让通信布局、专家矩阵形状和中间结果传递彼此匹配，从而减少访存往返，并创造通信与计算重叠的机会。它优化的是整条 MoE 数据路径，而不是单次 GEMM 峰值。

昇腾适配证据：组件已提供 MegaMoE 路径，实际收益与 DeepEP、grouped GEMM 的协同效率相关；服务级收益可按目标模型与请求分布完成联调测试。

这些设计真正改变的是什么

七项机制分别处理负载不均、串行生成、重复计算、CPU 空等和中间数据往返，但它们共享同一个思路：让模型结构决定并行方式，让调度理解计算阶段，让通信布局匹配专家 GEMM。其中不少技术并非 DeepInfer 首次提出，其差异化来自围绕单一模型和昇腾后端做联合调优。是否形成端到端优势，仍需用目标请求分布和完整服务链路验证。

DeepInfer 最初主要基于 vLLM 构建，并吸收了 SGLang 与 TensorRT-LLM 的设计思路，但它并没有走“覆盖尽可能多模型和硬件”的通用路线，而是把模型结构、稀疏注意力、MoE 通信与服务调度作为一个整体来优化。

与通用推理框架的根本差异

通用框架通常优先追求模型覆盖、硬件覆盖和接口稳定，因此更多依赖通用算子、通用内存布局和可移植调度。DeepInfer 则只支持 DeepSeek-V4.1-Flash，可以针对模型形状、稀疏模式、专家路由和 KV 格式做专门设计。

这类“垂直协同”会产生三个直接收益：第一，算子可以围绕固定形状和固定精度做极致调优；第二，通信可以理解 MoE 路由和 GEMM 时序；第三，调度可以把 Draft Token、SWA 重放和缓存布局共同考虑。代价是泛化能力弱、版本耦合强，且需要为每个硬件代际单独维护后端。

一句话理解 DeepInfer

它不是“另一个 vLLM”，更像一个为 DeepSeek V4.1 量身定制的推理参考实现与极限优化集合。与 vLLM / SGLang 的比较，不应只看 API 和通用功能数量，而应看特定模型在特定硬件上的端到端 Pareto 前沿。

开源边界：推理引擎核心与完整服务栈

README 明确说明 DeepInfer 支撑 DeepSeek 大规模生产服务，同时将本开源版本定位为离线推理与规模化服务核心能力。KV Cache 系统、VE / Prefill / Decode 分离、跨 DP 副本负载均衡归入完整服务系统，由外层组件承接。因此本次代码范围聚焦引擎核心与相关算子；跨实例缓存、请求编排和副本路由对应外层服务能力。

deepseek-recipe 不是这三项的补齐件。它负责 API 协议转换、Prompt 渲染、Tokenizer 编解码和流式输出解析；调用方仍须提供模型推理、工具执行与 HTTP 传输。

昇腾适配全景与实现深度

昇腾路径在构建、设备发现、运行时环境、通信、算子与 CI 六个层面都有独立实现。分析重点不仅是“能否运行”，还包括不同精度与内存接口对应的实现路径，以及由外层生产服务系统承载的能力。

LAYER 01 · BUILD

双加速器构建

DEEPINFER_ACCELERATOR=ascend 选择 `requirements-ascend.txt` 与 `NpuExtension`。

公共 C++ 调度器之外加入 `asc_utils.cpp` 和 `graph_timer_asc.cpp`，说明昇腾拥有独立编译产物。

LAYER 02 · RUNTIME

torch_npu 平台运行时

`transfer_to_npu` 将大量 CUDA 风格调用映射到 NPU；固定 TileLang 目标为 `ascend`，避免误探测为 CUDA。

配置 HCCL 缓冲与超时、可扩展显存段，并用 `aclrtHostRegisterV2` 固定主机内存。

LAYER 03 · TOPOLOGY

NPU 与 NUMA 感知

通过 `/dev/davinci*`、`/sys/class/ubcore` 和 `npu-smi` 发现设备、UB 实体与 NUMA 关系。

这意味着框架不只是调用单卡算子，而是尝试把进程、CPU 与 NPU 拓扑绑定。

LAYER 04 · COLLECTIVE

HCCL 与 DeepEP-Ascend

分布式后端为 `hccl`。DeepEP-Ascend 使用 HCCL / HCOMM、UBMEM、URMA 与 DeepJIT。

支持 EP dispatch / combine、FP8 dispatch 与延迟 epilogue；PP、Engram、Bucket 处于持续完善路径，使用前按目标版本核对。

LAYER 05 · KERNELS

Ascend TileLang 算子后端

覆盖 KV、采样、DFlash、SWA、CP、视觉与结构化输出。

FP8 scale 类型在昇腾为 `int16`，NVIDIA 为 `int32`，说明数据布局 ABI 已平台化。

LAYER 06 · GRAPH & CI

图执行与观测能力分层

NPU Graph 可捕获和 replay；NPU Graph Timer 已保留统一接口，平台事件实现可按目标 CANN 版本接入。

离线推理测试覆盖 2 节点 × 8 NPU，采用 EP16 / CP8 并行配置。

昇腾实现覆盖与后续扩展

EPLB 在线权重 shuffle 接口扩展

路由、负载统计与重排计算已具备；在线权重 shuffle 当前沿用 GPU 单机 IPC 路径，昇腾侧可沿平台对称内存接口继续扩展。

Sampler 场景 TopK 兼容路径

DeepSelect 的昇腾路径覆盖 BF16；需要 FP32 TopK 且返回 value 时由 `torch.topk` 承接。两条路径保持功能可用，后续可针对高频 Decode 增加专用实现。

Graph 内细粒度计时 观测接入

`graph_timer_asc.cpp` 已定义事件、同步、图句柄与计时接口；当前快照接入平台事件实现前，组件级耗时可使用 CANN profiling 工具补充。

FlashMLA 算子范围 目标范围

计算架构与芯片内数据流

DeepInfer 的昇腾优化不是把 GPU kernel 直接翻译为 NPU 代码，而是围绕昇腾的异构流水重新组织数据搬运、矩阵计算、向量变换和跨核同步。其设计重点是把 CUBE Core 持续保持在有效计算状态。

Prefill：计算受限，目标打满 CUBE

Prefill 阶段一次处理较多 query token，矩阵乘工作量足够大。FlashMLA 的昇腾实现为每个 AI Core 分配 64 个 query head，采用 1 CUBE + 2 VECTOR，把 softmax、反量化、ND2NZ 和 FixPipe 搬运分摊到两个 Vector Core。

流水上采用“当前块 QK、上一块 PV、后续块预取”的交错方式，使 CUBE 不等待 softmax；skip-scale 只在 online softmax 的最大值偏移超过阈值时执行 O 重缩放，减少 FixPipe 和向量计算。

Decode：数据与搬运更敏感

Decode 每步 query token 少、KV 历史长，算子更容易受 KV 读取、FP8 / FP4 反量化、索引 gather 和 FixPipe 影响。昇腾 Decode 达到 360 TFLOPS、约 83% 峰值，低于 Prefill 的 95%，与该结构性差异一致。

因此 DeepInfer 将 KV 的 data 与 scale 按 token 相邻存储，减少 MTE2 请求；使用 gather2 合并两 token 搬运；并在 UB 中完成 ND 到 NZ 的高吞吐转换。

八个关键微架构优化

ND

ND → NZ 片上转换

稀疏 KV 无法在 GM → L1 搬运时顺路完成 layout 变换，因此先进入 UB，再由 SIMD VF 完成转换，以避免 L2 访存合并失效。

KV

Token 交错 KV 布局

把每个 token 的 data 和 scale 相邻放置，使一次搬运可以同时取得二者，降低 Decode 的 MTE2 请求数和地址开销。

L1

双 L1 bank 均衡

把 Q、K、V 等张量拆分到两个 L1 bank，避免单 bank 带宽成为矩阵流水瓶颈，使 CUBE 的输入供给更稳定。

SF

昇腾专用 scale 布局

FP8 scale 使用 `int16` 成对打包，并以 MN-major 布局存放；这与 NVIDIA `int32` 路径不同，是为昇腾硬件效率服务的数据 ABI。

SS

Skip-scale 与跨核同步

通过 SS buffer 与 cross-core flag 在 VECTOR、CUBE 间传递“是否重缩放”，减少不必要的 FixPipe、UB 和向量运算。

G2

gather2 合并搬运

用一次 MTE2 请求搬运两个稀疏 token，降低 issue queue 压力，避免大量细小 gather 请求阻塞搬运管线。

IC

指令缓存控制

使用硬件循环、谨慎展开与函数内联，避免 CUBE / VECTOR / SIMD VF 的小容量指令缓存频繁换入换出。

FP

FixPipe 感知流水

把输出 accumulator 放在 UB，按块执行 FixPipe 搬出与 VECTOR 累加，避免在 L0C 上通过额外矩阵乘完成 rescale。

术语表

DSA
DeepSeek Sparse Attention，按索引只关注部分 KV token 的稀疏注意力。
CUBE / VECTOR
昇腾 AI Core 内的矩阵计算与向量计算执行单元。
UB / L1 / L0C
分别为统一向量缓冲、矩阵输入缓存和矩阵累加结果存储。
MTE2 / MTE3 / FixPipe
全局到片上、片上到 L1、矩阵结果搬出的关键数据搬运管线。
ND / NZ
常见行主序布局与昇腾矩阵计算偏好的分形布局，需要片上转换。
EP
Expert Parallel，MoE 专家分布在不同 rank 上的并行方式。
EPLB
Expert Parallel Load Balancing，根据负载重排专家放置。
CP
Context Parallel，将长上下文切分到多个 rank。
P/D 分离
Prefill 与 Decode 分别部署和调度，以匹配不同计算特征。
KV Cache 服务
跨请求、实例和层级管理 KV 的存储、复用、迁移与淘汰；区别于单个引擎内的 KV tensor 或分页加载接口。
deepseek-recipe
DeepSeek 开源的 API 协议适配与 Prompt / Token 编解码组件，不是推理引擎或服务编排系统。
TTFT / TPOT
首 token 延迟与后续每 token 输出时间，是推理 SLA 核心指标。
MFU
Model FLOPs Utilization，模型有效计算占硬件峰值算力的比例。
验证版 HDK
用于工程验证的硬件开发套件配置；此处特指非公开商用的手工配置。
HCCL / HCOMM
昇腾集合通信与底层通信组件。
URMA / UBMEM
DeepEP-Ascend 使用的远端内存访问与统一总线内存相关能力。
TFLOPS
每秒万亿次浮点运算，是吞吐单位；利用率等于实测 TFLOPS 除以对应精度的理论峰值。
GB/s
每秒十亿字节，用于描述显存、集合通信或网络的数据搬运带宽。
